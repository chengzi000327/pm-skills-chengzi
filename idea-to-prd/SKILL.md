# Idea → PRD v0(从想法到产品定义稿)

把一个还很粗的产品想法,通过多轮追问变成 **PRD v0 / 产品定义稿**,并产出 sample/eval 定义与"两图一表":原型草图、流程/状态图、数据表。这个 skill 的重点不是交付给研发的完整 PRD,而是帮助产品经理把问题、用户、场景、样本、评测标准、方案取舍、MVP 范围和完成标准想清楚,再把脑中的结构显性化。

它位于完整产品工作流的前段:

```
想法 -> 问题定义 -> Samples/Eval -> 共同能力 -> PRD v0+两图一表 -> PRD-to-Frontend -> Frontend-to-PRD -> 实现规格/开发计划
```

## 和其他 skill 的分工

- `product-decision`: 判断方向值不值得继续投入,适合更早期的方向验证和立项判断。
- `idea-to-prd`: 把已经想继续探索的产品想法梳理成 PRD v0 + Samples/Eval + 两图一表。
- `idea-to-frontend`: 基于 PRD v0 + 两图一表做界面/原型探索,本质是 PRD-to-Frontend。
- `prd-writer`: 基于 PRD v0 + 两图一表 + 原型发现,整理完整交付型 PRD / PRD v1,本质是 Frontend-to-PRD。

## 核心原则

**多问问题,不要急着写文档。** 用户给的初始想法通常只覆盖了"我要做什么",但缺少"为什么做、给谁做、边界在哪、怎么判断做对了"。进入输出前必须先追问。

**PRD v0 是思考工具,不是研发交付件。** 不需要一上来写字段、接口、状态机和测试用例;这些属于 `prd-writer` 的 PRD v1。

**评测即需求。** 对 AI 产品来说,需求不只写在 PRD 里,还写在 Sample、Rubric 和 Metric 里。先用具体 case 定义现状,再用 Rubric/Metric 定义理想态和完成标准。

**没有 3-5 个 sample,不输出 PRD v0。** 这是硬门,不是建议。用户还没给出足够 case 时,只能继续追问或先输出"缺失样本清单",不要用脑补的用户故事凑 PRD v0。

**从 case 抽象能力,再画两图一表。** 不要先画结构再倒推能力。先列代表性 samples,抽出共同能力和边界,再画原型草图、流程/状态图和数据表。

**两图一表是高质量 Prompt 的载体。** 原型草图表达"心中构想的样子",流程/状态图表达业务模式和状态边界,数据表表达业务现状、指标、对象和漏斗。它们共同让 AI 快速理解产品。

**每个结论都标出确定性。** 用户明确说过的写"已确认";合理推断写"推断";还缺信息写"待验证"。

## 流程

```
阶段0 想法复述 -> 阶段1 追问澄清 -> 阶段2 Sample/Eval定义与能力抽象 -> 硬门A 样本充足度 -> 阶段3 方案收敛 -> 阶段4 PRD v0+两图一表输出 -> 门0 用户确认
```

### 阶段 0:想法复述

先用 3-5 句话复述用户想法,不要扩写成方案。复述必须包含:

- 产品/功能一句话
- 可能的目标用户
- 可能的核心问题
- 当前最大不确定性

如果连目标用户或核心问题都无法推断,直接进入阶段 1 追问。

### 阶段 1:追问澄清

进入本阶段先读 `references/questions.md`。一次问 2-4 个问题,优先用选择题降低用户负担。粗想法至少追问两轮,除非用户已经提供了完整背景。

必须问清楚:

1. **目标用户**:谁在什么场景下会用。
2. **核心问题**:他们现在遇到什么痛点,现有方案为什么不够好。
3. **触发场景**:用户什么时候会想到使用这个产品。
4. **核心流程**:用户从哪里来,完成哪几步,最后得到什么。
5. **MVP 范围**:第一版必须做什么,明确不做什么。
6. **核心假设**:哪些判断如果错了,这个产品就不成立。
7. **评测样本**:3-5 个带完整 context 的典型 case。
8. **Rubric/Metric**:什么算好、怎么量化、谁来判断。
9. **成功标准**:怎么判断 v0 值得继续推进。

### 阶段 2:Sample/Eval 定义与能力抽象

进入本阶段先读 `references/eval-as-requirement.md`。AI 产品必须先把需求写成 Dataset(Samples + Context) + Rubric + Metric。

必须产出:

- **代表性 samples/cases**:至少 3-5 条,每条包含用户画像、当下情境、用户输入、期望输出、风险点、证据状态。
- **Rubric**:分层定义什么输出算好,什么输出不可接受。
- **Metric**:定义可统计的完成标准和阈值;Agent 场景要同时考虑 eval answer 和 eval trace。
- **共同能力抽象**:从 cases 里抽象出产品必须具备的能力,例如识别风险、补全上下文、调用工具、生成计划、解释原因、触发人工确认。

硬门 A:

- 少于 3 条 sample:不要进入方案收敛,继续追问补样本。
- 有 3-5 条 sample 但覆盖不均衡:可以继续,但必须标出缺口和待验证场景。
- 没有 samples/eval:不要进入两图一表,也不要输出 PRD v0。

### 阶段 3:方案收敛

不要只给一个方案。基于已知信息,给 2-3 个方案方向,每个方向写清:

- 适合的用户/场景
- 主要收益
- 覆盖哪些 sample 和共同能力
- 代价或风险
- 为什么推荐或不推荐

然后给出你的推荐方案。用户确认一个方案后,再输出 PRD v0。

### 阶段 4:PRD v0 + 两图一表输出

进入本阶段先读 `references/prd-v0-template.md`、`references/eval-as-requirement.md` 和 `references/two-diagrams-one-table.md`。输出要短而硬,避免八股和空话。

最终产出必须包含四块:

1. **PRD v0 / 产品定义稿**:背景与问题、目标用户与核心场景、目标与非目标、核心假设、推荐方案与取舍、MVP 范围、风险与待验证问题。
2. **Samples/Eval**:Dataset cases、Rubric、Metric、Judge/Evaluator、Protocol 和完成标准。
3. **共同能力抽象**:从具体 cases 抽象出这个产品必须具备的共性能力和边界。
4. **图一:原型草图**:用 ASCII wireframe 或低保真结构图表达模块、顺序、主 CTA 和页面信息架构。
5. **图二:流程/状态图**:优先用 Mermaid 表达用户路径、业务 pipeline、状态边界、异常/回退路径。
6. **一表:数据表**:根据场景选择业务对象表、漏斗/转化表、指标表、评测样本表或权限/角色表,让 AI 理解业务对象和评价标准。

如果下一步适合做界面探索,明确建议进入 `idea-to-frontend` 做 PRD-to-Frontend;如果仍然缺关键验证,建议回到用户访谈、数据调研或 `product-decision`。

## 禁止事项

- 不要在问题没问清楚时直接输出完整 PRD。
- 不要把 PRD v0 写成研发交付文档。
- 不要只写"专业/安全/个性化/可执行";必须用 sample + rubric + metric 定义。
- 不要没有 case 就抽象能力,也不要没有能力抽象就画两图一表。
- 不要省略两图一表;信息不足也要画,但标"待验证"。
- 不要编造用户数据、市场数据或访谈结论;没有证据就标"待验证"。
- 不要默认方案已经成立;核心假设必须可被证伪。

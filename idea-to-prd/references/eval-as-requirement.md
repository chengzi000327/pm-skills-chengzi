# 评测即需求

AI 产品不是确定性 CRUD。传统软件可以主要用流程、字段、状态、权限、异常来定义需求;大模型/Agent 产品交付的是概率型供给,同一个输入在不同 context 下会得到不同回答、计划、工具调用或执行轨迹。

因此,AI 产品的 PRD v0 不能只写"希望模型专业、安全、个性化、可执行"。这些形容词必须被拆成:

```text
Dataset(Samples + Context) + Rubric + Metric
```

- **Dataset / Samples + Context**:现状。模型会遇到哪些典型 case,用户是谁,处在什么状态,带着什么目标,提出了什么问题。
- **Rubric**:理想态。什么输出算好,什么算坏,优先级如何,不同质量层级怎么区分。
- **Metric**:量化方式。如何统计是否达标,阈值是什么,是否需要分场景统计。

一句话:评测即需求,评测即产品。Sample 是需求的原子,Dataset 是需求的分布。Rubric + Metric 定义产品的理想态。

## 在 PRD v0 中的位置

在进入两图一表之前,先做三步:

1. **列具体 cases**:至少 3-5 条代表性样本。不要只写用户需求,要写完整 context。
2. **抽象共同能力**:从 cases 里抽出产品必须具备的共性能力。
3. **定义评测标准**:为核心能力写 Rubric 和 Metric。

然后再画两图一表:

```text
Cases -> Dataset/Rubric/Metric -> 共同能力 -> 原型草图/流程状态图/数据表
```

## Case 写法

每条 case 至少包含:

| 字段 | 说明 |
| --- | --- |
| 用户画像 | 谁在使用,有什么背景/约束 |
| 当下情境 | 时间、状态、环境、上下文 |
| 用户输入 | 用户实际会怎么问/怎么操作 |
| 期望输出 | 理想结果的结构和边界 |
| 风险点 | 什么输出会伤害体验、安全、合规或业务目标 |
| 证据状态 | 已确认/推断/待验证 |

## Rubric 写法

Rubric 要分层,不要只写"好/不好"。

推荐结构:

- 必须满足:安全、合规、事实正确、边界清楚。
- 应该满足:个性化、完整性、可执行性、解释清楚。
- 加分项:体验自然、主动提醒、效率高。
- 禁止项:编造、越权、误导、鼓励危险行为、跳过关键确认。

## Metric 写法

Metric 必须能被统计。可以是人工评审、专家评审、LLM-as-a-Judge、规则程序或线上 feedback 校准。

常见指标:

- 风险识别召回率
- 不当建议出现率
- 个性化判断准确率
- 工具调用成功率
- 任务完成率
- 用户满意度
- 平均成本/延迟

对 Agent 场景,不仅要 eval answer,还要 eval trace:

- 工具是否选对。
- 参数是否正确。
- 中间状态是否一致。
- 出错后是否能纠正。
- token、延迟、费用是否失控。

## 输出原则

- 没有 sample 的需求,只是想法。
- 没有 rubric 的需求,无法判断什么算好。
- 没有 metric 的需求,无法指导迭代。
- 先用具体 case 抽象共同能力,再画两图一表;不要先画结构再倒推能力。

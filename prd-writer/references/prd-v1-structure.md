# PRD v1 结构与写作规范

PRD v1 是交付型文档,读者是研发、测试、设计、数据和评审人。它要把产品定义转成可实现、可测试、可追踪的规则。

## 推荐章节

### 1. 基本信息

| 项目 | 说明 |
| --- | --- |
| 功能名称 | 功能或模块名 |
| 所属模块 | 所属产品/业务模块 |
| 版本号 | vX.Y.Z |
| 负责人 | 产品/研发/设计/测试 |
| 预计上线时间 | 若未知写 `[待补充]` |

### 2. 更新记录

| 时间 | 作者 | 更新说明 |
| --- | --- | --- |

### 3. 背景与目标

写四件事,每条 1-3 句话:

- 背景:为什么做,现在有什么问题。
- 目标用户:谁在什么场景下用。
- 功能介绍:这个版本具体提供什么能力。
- 目标收益:做完后指标要变成什么样。

不要只写"提升体验";要写"把客服首响时间从 3 分钟降到 30 秒以内"这类可判断目标。

### 4. 需求来源与输入材料

把 PRD v0、Samples/Eval、两图一表、原型、数据结论和用户反馈列出来。

| 输入材料 | 关键结论 | 如何进入本 PRD |
| --- | --- | --- |
| PRD v0 | 产品目标、MVP 范围 | 转成背景、目标、范围 |
| Samples/Eval | 样本、Rubric、Metric | 转成测试集、验收、埋点 |
| 原型草图 | 页面模块、主 CTA | 转成页面结构和交互 |
| 流程/状态图 | 主流程、异常分支 | 转成流程定义和状态规则 |
| 数据表 | 对象、字段、指标 | 转成字段、接口、埋点 |

### 5. 范围定义

| 范围 | 内容 |
| --- | --- |
| 本期必须做 | P0 能力和交付边界 |
| 本期不做 | 明确排除,避免研发脑补 |
| 后续可能做 | P1/P2 或待验证能力 |

### 6. 用户流程 / 业务流程

必须包含:

- 流程图。
- 节点说明表。
- 正常路径。
- 异常/回退路径。
- 状态切换条件。

流程图画法见 `flowchart-svg.md`。

### 7. 功能点详细说明

每个功能点单独成节,固定写:

| 模块 | 必写内容 |
| --- | --- |
| 触发条件 | 用户动作、系统事件、定时任务、外部回调 |
| 输入 | 用户输入、系统读取、依赖服务、上下文 |
| 核心逻辑 | 判断规则、计算逻辑、优先级、状态变更 |
| 输出 | 页面结果、接口返回、消息通知、数据写入 |
| 字段/状态 | 字段类型、枚举、校验、默认值 |
| 异常 | 失败条件、提示文案、回退方案、是否可重试 |
| 权限 | 谁能看、谁能操作、越权怎么处理 |
| 埋点/验收 | 对应事件、Metric、测试用例 |

### 8. 数据与接口

若有后端或数据读写,必须写:

- 核心对象与字段。
- 新增/变更接口。
- 读写时机。
- 幂等、重试、并发、权限。
- 错误码。

### 9. 埋点、验收与测试

Metric 不能只写在目标里。按照 `metrics-acceptance-tracking-tests.md` 把每个 Metric 转成:

- 验收标准。
- 埋点事件或离线统计口径。
- 测试集/评测集。

### 10. 风险与待确认

列出业务风险、体验风险、技术风险、合规风险和待确认问题。

## 写作风格

- 用"操作 -> 触发 -> 结果"写逻辑。
- 少用"它、该功能、上述操作";直接写按钮名、状态名、字段名。
- 能列表不写长段落。
- 复杂逻辑用判定表,不要用一大段 if-else。
- 默认行为必须写出来:未登录、无网、空数据、加载中、权限不足、重复点击、返回键、失败重试。

## 模糊处处理

- 能合理推断的:直接写规则,旁边标 `[TODO: 待确认]`。
- 真的不清楚的:用 `[待补充: 需确认 xxx]` 占位。
- 文末统一汇总待确认清单。

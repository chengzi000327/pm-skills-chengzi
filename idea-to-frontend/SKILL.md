# Idea → Frontend(从想法到前端页面)

把一个还很粗的想法,经过四个阶段做成有设计感、可预览的前端页面。覆盖两类界面:**落地页 / 营销官网**(设计本身就是产品)和 **App / 产品功能界面**(设计服务于功能)——这两类的设计逻辑不同,在阶段 1 会区分对待。

最终代码形态**按项目选**:简单页面用单文件 HTML + Tailwind(预览最快),组件化/有状态的用 React。风格**每个项目重新定**,不用固定 house style。

## 最重要的一条:走流程,不要跳过门直接写代码

最常见的失败模式是:用户给一句想法,模型脑补一套需求就直接开始写一整页代码,结果方向全错。本 skill 的价值就在于**用四个门挡住这种冲动**。每个阶段结束都要停下来等用户确认,确认了才进下一阶段。

```
阶段0 发现访谈  ──门0──>  阶段1 定风格(给2-3个方向)  ──门1──>  阶段2 ASCII线框  ──门2──>  阶段3 落地代码  ──>  交付前自检
```

- **门 0 / 门 1 / 门 2 是硬门**:没拿到用户明确的"就这个方向 / 继续"之前,不要往下做。把自己写的总结当成用户的确认,是要避免的。
- 如果用户明确说"别问了直接做"或需求已经很完整,可以压缩前面的阶段,但**至少要在写代码前把风格方向和线框口头过一遍**。

---

## 阶段 0:发现访谈

目标:在画任何东西之前,搞清楚"做什么、给谁看、最想让访客做什么动作、什么气质、最讨厌什么样子"。

完整问题清单和提问方式见 `references/discovery.md`,**进入本阶段时先读它**。核心是几个绕不开的点:这是落地页还是产品界面、产品一句话是什么、目标用户、希望访客完成的那一个动作(CTA)、品牌气质词、以及 **anti-reference(最讨厌的同类页面长什么样)**。

提问时一次别问太多,优先用选择题降低用户负担(在 claude.ai 移动端尤其如此)。问完做一句话的需求复述,这就是**门 0**:用户点头才进阶段 1。

---

## 阶段 1:定风格(给 2-3 个方向,让用户挑)

这是本 skill 最核心的一步,也是最容易出 "AI 味" 的一步。**进入本阶段先读 `references/style-directions.md` 和 `references/inspiration-sources.md`。**

做三件事:

1. **拉真实参考(关键)**。本 skill 不自带页面库,也无法自动爬 mobbin/variant。真正"找合适的设计页面"是靠在这一步主动检索:按 `references/inspiration-sources.md` 的检索 playbook,用 `web_search` / `image_search` 拉一组和产品气质匹配的真实页面/截图摆给用户看(工具可用性见该文件说明)。

2. **反收敛自检**。在提任何字体/配色前,先在心里说出你的前 3 个直觉,然后**否决它们**——因为那通常就是所有 AI 都会给的那套(Inter / Space Grotesk、白底紫渐变、千篇一律的卡片堆卡片)。再做 inverse test:用竞品的话术描述你这个方向,如果一句话套得上同品类任何一个页面,推倒重选。具体清单见 `references/style-directions.md`。

3. **给 2-3 个有区分度的方向**,每个方向包含:一个气质名 + 一句话定位、display 字体 / 正文字体、配色(主色 + 强调色 + 背景,用 hex)、版式骨架特征、动效基调、以及 1-2 个真实参考链接/截图。三个方向之间要**真的不一样**(不是同一套换个主色)。

输出后这是**门 1**:用户选定一个方向(可以让他混搭"要 A 的配色 + B 的版式")才进阶段 2。

---

## 阶段 2:ASCII 线框

目标:在写代码前,用纯文本线框把**信息架构和每个区块放什么**敲定,改起来零成本。

约定和示例见 `references/wireframe.md`。要点:从上到下逐区块画(落地页常见:Hero → 价值点 → 功能/玩法 → 社会证明 → 定价/CTA → 页脚;产品界面则按导航 + 主内容区 + 操作区画),每个区块标注里面有什么文案/元素/交互。同时给出移动端的堆叠顺序(因为最终必须响应式)。

线框确认是**门 2**:用户点头才写代码。

---

## 阶段 3:落地代码

**进入本阶段先读 `references/build.md`**,它讲清楚 HTML 路线和 React 路线分别怎么搭、在当前环境怎么给用户预览、以及"代码复杂度要匹配设计野心"这条原则。

按项目选形态:
- **单文件 HTML + Tailwind**:简单落地页 / 营销页首选,预览最快。
- **React(.jsx)**:有交互状态、组件复用、或属于产品界面时用。

落地时严格执行阶段 1 定下的风格,不要中途漂回"通用现代 SaaS"那套。把字体真的引进来、配色用 CSS 变量统一、该有的动效和细节做到位。

---

## 交付前自检(每次给代码前都过一遍)

写完代码、给用户之前,**对照 `references/anti-slop.md` 的清单逐条自检**。这一步是最后一道反 AI slop 的关卡:被点名的字体、配色 tell、版式 tell、对比度、可点击元素的 cursor、reduced-motion、响应式断点、别拿 emoji 当图标等等。自检发现问题就地改掉再交付。

---

## 用 subagent 提速(仅当环境支持)

subagent(并行子代理)在 **Claude Code / Cowork 里有,claude.ai 网页/App 里没有**——先确认环境,没有就全部串行执行,流程和产出不变。

关键认知:本流程**带门、要等用户确认,所以阶段之间不能并行**(阶段 2 依赖阶段 1 的拍板)。能并行的只是**单个阶段内部、不需要用户在场的重活**,即"检索"和"审查"。三个真正划算的并行点:

1. **阶段 1 拉参考(最划算)**:不要串行地一个方向一个方向搜。给每个风格方向开一个 subagent,各自跑 image_search + web_search + 必要的 fetch,带回挑好的参考。3 个方向并行 ≈ 1 个方向的耗时。
2. **阶段 1 生成方向 + 防撞车**:把 2-3 个方向分给 2-3 个 subagent,并**给每个指定一条不同的气质赛道**(如 A=编辑感 / B=技术终端 / C=温暖有机)再让它们各自做满字体/配色/版式/参考。指定赛道很关键——否则独立 agent 会各自滑向最大公约数反而更易撞车。等于并行同时换来提速 + 强制差异化。
3. **交付前自检派独立评审**:别让写代码的 agent 回头审自己的代码(最容易看不出 slop)。开一个全新 subagent,只给它成品 + `references/anti-slop.md`,当"没参与过的设计评审"挑毛病;需要时再拆成排版/配色/响应式几路并行。主要是质量收益,顺带提速。

不要硬上:发现访谈(一段对话)、三个确认门(本质是等人)、单页落地构建(一个文件,拆了反而乱)。只有交付物是**多页/多组件**时,阶段 3 才值得按页/按组件并行。

一句话:subagent 压缩的是"搜索 + 审查"耗时,压不了"等用户确认"的耗时。
